# Function Calling vs MCP: Обоснование архитектурного решения

## Введение

В процессе разработки телеграм-бота для управления Google календарем было рассмотрено два подхода к интеграции LLM с внешними API: Function Calling (Tool Calling) и Model Context Protocol (MCP). В результате анализа требований проекта выбран подход Function Calling. Данный документ описывает обоснование этого решения.

---

## Function Calling: Выбранный подход

Function Calling — это нативный механизм работы современных LLM (GPT-4, Claude 3.5, Llama 3) для вызова внешних функций. Функции описываются в JSON-схеме, отправляются вместе с промптом в LLM API (в данном проекте — OpenRouter), модель определяет необходимость вызова функции и возвращает аргументы, после чего приложение выполняет функцию и возвращает результат модели.

### Преимущества для данного проекта

**Простота архитектуры**: Вся логика находится внутри одного Python-приложения (бот + интеграция с Google Calendar API). Отсутствует необходимость в дополнительных серверах и протоколах.

**Нативная совместимость с OpenRouter**: OpenRouter полностью поддерживает OpenAI-compatible Tool Calling. Библиотеки Aiogram и OpenAI SDK поддерживают этот механизм из коробки, что упрощает интеграцию.

**Производительность**: Отсутствие промежуточного слоя в виде MCP-сервера снижает сетевые задержки и упрощает обработку запросов.

**Гибкость обработки ошибок**: Прямая интеграция позволяет легко обрабатывать ошибки API (например, занятый слот в календаре) и сразу запрашивать уточнения у пользователя в контексте диалога.

**Управление аутентификацией**: Каждый пользователь имеет собственный OAuth refresh token, хранящийся в базе данных бота. При обработке запроса токен пользователя используется для инициализации клиента Google Calendar API. Это стандартный подход для мультипользовательских приложений.

### Недостатки

Код интеграции с Google Calendar API жестко привязан к коду бота, что снижает возможность переиспользования в других приложениях.

### Пример потока выполнения

```
Пользователь: "Встреча завтра в 14:00"
  ↓
Бот отправляет запрос в OpenRouter с описанием функции add_event
  ↓
OpenRouter возвращает JSON: {name: "add_event", args: {time: "2023-10-27T14:00...", title: "Встреча"}}
  ↓
Бот выполняет вызов Google Calendar API с токеном пользователя
  ↓
Бот возвращает результат: "Событие добавлено в календарь"
```

## MCP: Альтернативный подход

Model Context Protocol (MCP) — протокол, разработанный Anthropic для стандартизации подключения инструментов к LLM. Подход предполагает создание отдельного MCP-сервера, который реализует работу с Google Calendar, и подключение его к клиенту (боту) через протокол MCP.

### Преимущества MCP

**Переиспользование кода**: При наличии готового MCP-сервера для Google Calendar можно использовать его без написания собственной интеграции.

**Модульность**: Один и тот же MCP-сервер может быть использован в разных приложениях (десктопный клиент, веб-приложение, бот) без изменений.

### Недостатки для данного проекта

**Отсутствие нативной поддержки в OpenRouter**: OpenRouter и OpenAI SDK не поддерживают протокол MCP напрямую. Требуется реализация моста (MCP Client), который:
- Получает список инструментов от MCP-сервера
- Конвертирует их в JSON-схему для OpenRouter
- Получает ответ от LLM
- Пересылает вызов обратно на MCP-сервер

Это добавляет 100-200 строк сложного кода и дополнительный слой абстракции.

**Усложнение инфраструктуры**: Требуется управление отдельным процессом MCP-сервера и поддержка связи с ним.

**Проблемы с мультитенантностью**: Стандартные MCP-серверы рассчитаны на single-tenant архитектуру (один пользователь, локальное использование). Для поддержки множества пользователей с разными OAuth токенами потребуется либо:
- Запуск отдельного инстанса MCP-сервера для каждого пользователя (неэффективно)
- Модификация MCP-сервера для поддержки мультитенантности (значительно усложняет архитектуру)

## Обоснование выбора

### Ключевой фактор: Мультипользовательская архитектура

Основная проблема MCP для данного проекта — управление аутентификацией множества пользователей.

**Требования проекта**:
- Поддержка множества пользователей (каждый со своим Google Calendar)
- Хранение OAuth refresh tokens в базе данных
- Динамическая инициализация клиента Google Calendar API для каждого пользователя

**Function Calling**:
- Прямой доступ к токенам пользователей из базы данных
- Простая инициализация клиента API для каждого запроса
- Стандартный подход для мультипользовательских приложений

**MCP**:
- Стандартные MCP-серверы не поддерживают мультитенантность из коробки
- Требуется значительная доработка или запуск множества инстансов
- Усложнение архитектуры без существенных преимуществ для данной задачи

### Дополнительные факторы

1. **Совместимость с OpenRouter**: Function Calling поддерживается нативно, MCP требует дополнительного слоя абстракции.

2. **Простота разработки и поддержки**: Меньше компонентов, меньше точек отказа, проще отладка.

3. **Производительность**: Отсутствие промежуточного слоя снижает задержки.

---

## Заключение

Для телеграм-бота управления Google календарем выбран подход Function Calling по следующим причинам:

1. **Мультитенантность**: Простое управление аутентификацией множества пользователей
2. **Совместимость**: Нативная поддержка OpenRouter и стандартных библиотек
3. **Простота**: Меньше компонентов и инфраструктурных сложностей
4. **Производительность**: Отсутствие промежуточных слоев

MCP имеет смысл использовать в случаях, когда:
- Один и тот же набор инструментов используется в нескольких разных приложениях
- Разрабатывается сложная мульти-агентная система
- Уже существует готовый MCP-сервер, идеально подходящий под задачу

Для данного проекта Function Calling обеспечивает оптимальный баланс между простотой, производительностью и функциональностью.
